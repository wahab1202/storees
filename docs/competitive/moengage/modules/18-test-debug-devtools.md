## 18. Test & Debug tools, event log & integration guide

Storees has no Test & Debug area, but its admin debugging is stronger than MoEngage's here: the Event Debugger (server-side filters plus a Sessions panel for identity stitching), the Event Sources webhook debugger and Notification Logs go well beyond a 50-event Recent Events log, and Settings > SDK & Integration hands out copy-ready snippets with the project's own key where MoEngage only links to docs. The gaps are activation and self-serve: no setup checklist, integration banner, help menu or published docs, a "Send Test Event" that succeeds without touching the real integration, an SDK badge that reads "Not Connected" for pixel-only stores, and server-side `/api/v1` endpoints that accept the public browser key (P0, as in module 14). MoEngage's QR device tools need a mobile SDK that Storees does not have, and Jinja AI has nothing to target until Storees adds template logic.

### MoEngage overview

MoEngage groups its developer tools in a "Test and Debug" sidebar flyout and handles integration onboarding through a Setup Guide, an "integration pending" banner and a "Need help" menu.

- **Test and Debug flyout:** Integration Validation, SDK Logger, Segment Payload and Jinja AI. A fifth item, "Recent Events" (`/v4/developers/activity`), exists in the menu config but is hidden by the flag `SHOULD_HIDE_RECENT_ACTIVITY` in this workspace. Jinja AI is gated by `JINJA_AI_ENABLED`.
- **Integration Validation (Android only):** pair a device by QR code, enable the in-app "MoEngage Validator" debugger, then pick the device in Session Logs. From the page bundle: a guided checklist (Data Tracking, Basic Push, Push Templates) with eight per-check statuses, manual steps that listen for 60 seconds after "Yes, I performed the action", automatic checks such as notification icons, and "Send test push" in foreground, background and killed states.
- **SDK Logger:** stream a QR-paired device's SDK logs into the dashboard, with a level filter, search, copy session ID and "Fetch more". Supported only on Android-based SDKs (Native 13.4.00+, React Native 10.3.00+, Flutter 9.0.0+, Cordova 9.0.0+, Capacitor 5.0.0+).
- **Segment Payload:** build a segment in the standard filter UI (User property, User behavior, User affinity, Custom segment; "+ Filter" with AND/OR; "+ Nested Filter") and turn it into copyable JSON for the Custom Segment API. Generation is client-side, with name and filter validation.
- **Jinja AI (Beta):** a Merlin assistant that writes or fixes MoEngage Jinja from a plain-language prompt and explains it. The prompt can be grounded on a saved template or an uploaded HTML file. There are 4 starter cards and a 9-prompt "Sample Prompts" modal. From the bundle: Code and Explanation output with Copy and Download, a Test Code preview against a chosen user, "Fix with AI" and accuracy feedback.
- **Recent Events (flag-hidden):** from the bundle, the last 50 events received (User Id, Activity Time, Event Action, Event Attributes, Platform), with a notice when nothing has arrived for an hour.
- **Setup Guide:** a "Welcome, back!" popup; a "Welcome, [first name]!" card with a 3-step checklist and progress bar (Integrate, Invite team members, Create a new campaign); "What can you do with MoEngage?" tabs; a product tour; a demo account; plan links; a 16-digit subscription-code upgrade; Knowledge Base links.
- **Integrate drawer:** cards for the Web, iOS and Android SDKs, Validate integration, Partner guide and Data API. All link out to docs; no App ID, keys or code snippets appear in the app.
- **Help prompts:** an "Your integration is pending!" banner on list pages with "Get started with integration!" and "Check Event Log", and a top-bar "Need help" menu (Help center, Ask AI, Support, demo account, product ideas, Setup guide, Use cases, Integration guide, Academy).

- **Recent Events** is hidden by a feature flag; both direct navigation and "Check Event Log" redirect to All Campaigns. Its UI is described from the code bundle.
- **Live device sessions** in Integration Validation and SDK Logger need a real Android device; the QR codes encode empty values in this workspace. The checklist and log viewer are described from the page bundles.

- **No side effects:** nothing was saved, generated, sent, uploaded or downloaded.

### Storees-only strengths

- **Sessions debugger for identity stitching** (`debugger/page.tsx:208-296`; `routes/events.ts:115-207`). Sessions from the last 7 days, the phone or email seen in their payloads, whether each linked to a customer, and how many events were back-attributed. It answers "I typed my phone at checkout, so why didn't my browsing link to me?", the main failure mode for Shopify plus third-party checkouts. None of MoEngage's debug tools show identity resolution.
- **Event log filtered on the server, with session drill-down** (`debugger/page.tsx:65-99,141-149`; `routes/events.ts:31-97`). Customer name, email, phone or external ID; event name; date range; session; clickable session chips. Support can find one customer's events on a given date even when they are far outside the latest page, whereas Recent Events shows the last 50 with no filters.
- **Inbound webhook debugger** (`event-sources/[id]/page.tsx:82-273`; `routes/inboundWebhooks.ts:128-250`). Raw receipt log with headers, "Why didn't this match?" per rule, "Reprocess no-match rows" and a Schema tab inferred from payloads, so non-developers can connect and debug third-party payloads.
- **Notification delivery logs** (`logs/page.tsx:49-150`; `routes/logs.ts`). Channel, status and source filters, failure and block reasons, and Total / Delivered / Read / Clicked / Failed / Blocked counts. Answers "why didn't customer X get the WhatsApp?"; MoEngage's Test & Debug group has no delivery debugger.
- **Outbound webhook test and delivery log with resend** (`settings/webhooks/page.tsx`; `routes/webhookSubscriptions.ts:178-223`). Customers can check that their downstream systems receive Storees events, with status codes, responses and retries.
- **Connector test (raw vs mapped record) and per-run sync logs** (`components/data-sources/ConnectorsSection.tsx:110-246`; `SyncHistoryTable.tsx:107-145`; `routes/dataConnectors.ts:220,338`). Checks a pull integration's field mapping before a full sync, with logs filterable by level. The UI is super-admin-only today.
- **Rule-based template linting** (`templateLint.ts:45-105`; `templateLinter.ts:60+`; `routes/templates.ts:329-332`). Catches unmapped variables, bad formats, empty WhatsApp positional parameters and Meta rejection causes before anything is sent, so debugging personalisation needs no AI.
- **Shopify Customer Events pixel generated per project** (`settings/page.tsx:234-247`; `lib/shopifyPixel.ts`). Browse, cart and checkout tracking with no theme edits and no developer, which fits Shopify D2C merchants.
- **PII guard at ingest and role-based masking in debug views** (`middleware/dataMasking.ts:51-166`, mounted on the `/api/v1` event routes at `v1Events.ts:109` but not on `/api/v1/import`; `routes/events.ts:88-92,172-199`). Rejects card and Aadhaar numbers and masks account numbers; debug views hide contact details from roles without `viewContactPii`. Supports India's DPDP law; MoEngage only links to docs about PII masking.
- **Recommended events per vertical, with copyable `track()` examples** (`settings/page.tsx:18-45,273-303`). Integrators get the exact event names that packs, segments and flows expect, which prevents silent misnaming such as `add_to_cart` vs `added_to_cart`.
- **Self-serve data repair** (`settings/DataMaintenance.tsx`; `routes/customers.ts:845`). "Recalculate aggregates" and "Materialise event-only orders" let admins fix drifted order counts and CLV themselves.
- **Recent Activity card on the dashboard** (`dashboard/page.tsx:341-372`; `routes/dashboard.ts:318-350`). Shows at a glance, to every role, whether events are arriving, though it does not link to the Event Debugger.

### UX notes

- **Navigation** (screenshot 001 vs `Sidebar.tsx:54-71`). MoEngage keeps every developer tool in one "Test and Debug" flyout at the bottom of the sidebar, with "Test & Debug > Tool" breadcrumbs (002, 006, 007), so marketer navigation stays clean. Storees lists Event Sources, Event Mapping (super-admin), Event Debugger and Notification Logs as flat top-level items between Flows and Settings. Adopt a collapsible "Data & Debug" group.
- **Activation banner** (001 vs `settings/page.tsx:57,167-192`). MoEngage shows "Your integration is pending!" on list pages with "Get started with integration!" and "Check Event Log". Storees' only signal is the SDK Connection badge, two clicks deep (`/settings` opens on Channels). It counts only `source='sdk'` events, so a store that installed only the recommended Shopify pixel is told "Not Connected", and its "Not Connected" pill is hard-coded `text-yellow-400` on a light background, which is hard to read and breaks the design-token rule. Add a banner in `AppShell` next to `TrialBanner`, driven by recent pixel, SDK and webhook data, linking to Setup and `/debugger`.
- **Setup guide** (025-031 vs `dashboard/page.tsx:351-354`). MoEngage's Setup Guide combines a checklist with a progress bar, a "Welcome, back!" modal, capability tabs with one-click "Create" links, and cards for the tour, demo, plans and docs. Storees sends new sign-ups and Shopify installs straight to the metrics dashboard (`register/page.tsx:66`; `oauth/shopify/callback/page.tsx:50`), where the only hint is "No activity yet. Send your first event…". The checklist API already exists but nothing renders it (`v1Onboarding.ts:421-489`). For the self-serve Shopify trial, add a "Get started" card to `/dashboard` (Shopify connected, pixel installed, WhatsApp connected, team invited, first flow live); it would close the checklist, banner and validation rows together.
- **Integration instructions** (032 vs `settings/page.tsx:156-333`). Storees is ahead here: MoEngage's Integrate drawer only links to external docs, while Storees gives copy-ready Script Tag, Shopify pixel, NPM and REST snippets with the project's own key and URL. Three improvements: make Setup the default sub-section; replace the pixel's step 4 text (`settings/page.tsx:244`) with a live "waiting for the first added_to_cart…" check that links to `/debugger`; and borrow MoEngage's hover reference images (003, 004) to show Shopify's Customer events screen.
- **Event log** (`debugger/page.tsx`). Storees' Event Debugger beats a 50-event log, but:
  - the header's green pulsing "Live" icon shows even when nothing has arrived for days (line 43), which reads as healthy; pair it with a "no data in the last N hours" notice and a troubleshooting link;
  - there is no external user ID column, although the API returns it;
  - the dashboard's Recent Activity card has no "View all" link to the debugger;
  - the Sessions error state shows developer copy to customers ("the backend may not be updated/restarted (needs GET /api/events/sessions)", line 215);
  - platform badge colours are hard-coded Tailwind classes (lines 198-205).
- **AI prompting** (019, 021, 022 vs `templates/ai/page.tsx`). Jinja AI pairs the prompt box with starter cards, an "Explore more prompts" modal and a "+" menu that grounds the prompt on a template or HTML file. Storees' AI Email Designer has a similar prompt-and-result layout but starts from a blank brief, and the segment AI's only examples are fintech ones (`AiChatPanel.tsx:340-344`) that ecommerce brands also see. Add vertical-aware starter prompts to every AI tool.
- **Segment builder** (007, 014-017 vs `SegmentFilterBuilder.tsx`). MoEngage collapses a finished filter into a one-line description, puts copy and remove icons on each block, and turns the result into JSON. Storees shows `filterSummary` only on the segment list, offers remove but not duplicate, and its rule-row remove button is icon-only with no `aria-label` (line 544). Collapsible cards with a duplicate action would help long nested segments; a "Copy as API request" button is cheap once a key-authenticated segment API exists.
- **Help access** (033 vs `AppShell.tsx`; `Sidebar.tsx:219-245`). MoEngage keeps a "Need help" menu in the top bar. Storees has no top bar or help entry point and no support contact anywhere in the frontend. Self-serve Shopify trials need a help menu with docs, a WhatsApp or email support link and the setup checklist.
- **Honest validation** (`v1Onboarding.ts:496-536`; `onboarding/page.tsx:899-917`). The wizard's "Test your integration" button writes a synthetic `test_event` straight into the database and shows "Event received!", so it passes even when the integration is broken, and that row also marks the checklist's "first event received" step done. MoEngage's validation passes only on real SDK traffic (002, 004). Validate by waiting for the first real `/api/v1` event, pixel event or webhook.
